`groot init` is the starting point for every groot project. It plants a fresh bun-first Turborepo workspace, wires your chosen frameworks together, and leaves you with a working `bun dev` — all in one command. Run it interactively to pick your stack from a menu, or pass flags to script it end-to-end in CI.

## Synopsis

```sh
groot init [dir] [flags]
bun create groot [dir] [flags]
bunx create-groot@latest init [dir] [flags]
```

When you invoke `bun create groot`, bun resolves to the `create-groot` npm package and routes the bare positional argument to `init` automatically. The `bunx create-groot@latest` form always runs the newest published version.

## What it does

`groot init` runs a five-stage pipeline:

1. **Resolve** — combines your CLI flags, an optional `--preset`, and interactive prompts to produce a concrete plan: one framework per slot (web, mobile, api, backend).
2. **Preflight** — confirms Bun ≥ 1.2 is available, checks the target directory, and verifies any required network connectivity before writing a single byte.
3. **Generate** — calls the official upstream generator for each selected framework (e.g. `create-next-app`, `create-expo-app`) or writes files directly when no upstream generator exists.
4. **Stitch** — patches the workspace for coherence: updates root `package.json` workspaces globs, writes shared tsconfig paths, and wires cross-cutting integrations (e.g. a Next.js app importing from a Convex backend package).
5. **Verify** — runs `bun install`, runs `git init` + an initial commit, and confirms the Turborepo task graph is resolvable.

See [How it works](/concepts/how-it-works) for the full architecture breakdown.

## Interactive mode

Running `groot init` without slot flags launches the interactive prompt flow powered by [clack](https://github.com/natemoo-re/clack). Prompts run only for the slots you haven't already fixed with flags — mixing flags and prompts is fully supported.

```text
🌱 groot v0.5.0 — plant a bun-first Turborepo and grow it.

◆  Web app?      › Next.js
◆  Mobile app?   › Expo
◆  API?          › Elysia
◆  Backend?      › Convex

◇  Planting turborepo trunk…
◇  Growing apps/web (Next.js)…
◇  Growing apps/mobile (Expo)…
◇  Writing apps/api (elysia)…
◇  Writing packages/backend (convex)…
◇  Stitching workspace…
◇  Installing workspace (bun install)…
◇  Initializing git repository…
◇  Publishing to GitHub…

🌳 I am groot — your workspace is planted.
✓ GitHub: https://github.com/you/my-app
```

When you pass `--github`, the plan summary shown before you confirm includes a `github` row so you see the publish step ahead of time:

```text
◆  Your plan
│  web        next
│  api        elysia
│  backend    convex
│  github     create private repo + push initial commit (gh)
│
◇  Plant it? › Yes
```

Pressing **Ctrl-C** at any prompt exits immediately with code `130` and writes nothing to disk.

## Flags

| Flag | Values | Default | Description |
|---|---|---|---|
| `dir` | string | prompted | Target directory |
| `--name` | string | dir basename | Workspace / root package name |
| `--web` | `next` \| `sveltekit` \| `none` | prompted | Web app in `apps/web` |
| `--mobile` | `expo` \| `none` | prompted | Mobile app in `apps/mobile` |
| `--api` | `elysia` \| `hono` \| `fastify` \| `none` | prompted | API in `apps/api` |
| `--backend` | `convex` \| `none` | prompted | Backend in `packages/backend` |
| `--preset` | path | — | Read slot selections from a `groot.json` file or workspace |
| `--yes`, `-y` | — | off | Accept defaults for un-flagged slots |
| `--dry-run` | — | off | Print the resolved plan; write nothing |
| `--json` | — | off | With `--dry-run`: emit machine-readable plan on stdout |
| `--no-install` | — | install on | Skip root `bun install` |
| `--no-git` | — | git on | Skip `git init` + initial commit |
| `--github` | — | off | After the initial commit, create + push a private GitHub repo via `gh` — see [GitHub publishing](#github-publishing) |
| `--public` | — | off | With `--github`: create the repository as public instead of private |
| `--dir-conflict` | `error` \| `merge` \| `increment` | `error` | Policy for a non-empty target directory |
| `--keep-failed` | — | off | Keep the target dir if a generator fails |
| `--verbose` | — | off | Stream generator output instead of spinners |
| `--version`, `-v` | — | — | Print the groot version and exit |
| `--help`, `-h` | — | — | Print command help and exit |

## --yes defaults

<Note>
When you pass `--yes` without explicit slot flags, groot picks `--web next --mobile none --api none --backend convex` — a Next.js web app wired to a Convex backend. This is groot's flagship pairing and the fastest way to get a production-ready fullstack workspace on the ground.
</Note>

## Using a preset

`--preset <path>` points groot at an existing `groot.json` — either the file directly or a workspace directory that contains one — and uses it as the selections source for any slots you haven't fixed with flags.

```sh
# Replicate the shape of an existing workspace
groot init my-app --preset ../flagship
```

A few rules govern preset behaviour:

- Only the slot → framework shape is read. Workspace name, destination paths, ports, generator pins, and `conventions` always come from the current CLI invocation — a preset written by an older groot never pins stale generators.
- Explicit slot flags always win over the preset. Slots absent from the preset resolve to `none`.
- With a target directory given, a preset run is fully non-interactive.
- The preset is validated like any manifest — unknown framework IDs or manifest versions exit with code `2`.
- If a manifest grew multiple scaffolds into one slot via `groot add --path`, the preset uses the first one per slot and warns about the rest; replicate them afterwards with `groot add --path`.

See [Presets](/guides/presets) for a deeper walkthrough.

## Dry run

Pass `--dry-run` to print the resolved plan without writing anything to disk. Add `--json` to emit the `groot.json` manifest to stdout instead — useful for inspecting the plan in CI or piping it into another tool.

```sh
groot init my-app --web next --backend convex --dry-run --json
```

The command exits `0` and nothing is written to disk. In `--json` mode, all diagnostics (preflight checks, warnings) go to stderr so stdout remains pure machine-readable output.

## Non-interactive example

```sh
bunx create-groot@latest init my-app \
  --web next --mobile expo --api elysia --backend convex --yes
```

Every slot is fixed by a flag, `--yes` suppresses the confirmation prompt, and there is no TTY requirement — safe to run in any CI environment.

To plant a workspace and publish it to GitHub in a single command, add `--github` (and optionally `--public`):

```sh
bunx create-groot@latest init my-app \
  --web next --backend convex \
  --yes --github
```

groot runs the full pipeline, makes the initial commit, then creates a private GitHub repository and pushes to it via [`gh`](https://cli.github.com). Add `--public` if you want the repository to be public instead. If `gh` isn't installed or isn't logged in, the workspace is still planted successfully — groot prints the manual commands to run yourself (see below).

## GitHub publishing

Passing `--github` extends the [Verify](/concepts/how-it-works) stage with a publish step that runs **after the initial commit**:

1. `Bun.which("gh")` — detect the [GitHub CLI](https://cli.github.com) on `PATH`.
2. `gh auth status` — confirm you are logged in to at least one host.
3. `gh repo create <name> --private --source=. --remote=origin --push` — create the repository and push the initial commit. `--public` swaps `--private` for `--public`; the repository name is the workspace name (from `--name` or the target directory basename).

When it succeeds, groot prints the repository URL on its own line and surfaces the same fact in the plan summary, dry-run output, prompt confirmation, and next-steps report:

```text
✓ GitHub: https://github.com/you/my-app
```

### Preconditions (checked before anything is generated)

These are usage errors — groot exits `2` and writes nothing, so a dry run that would fail for real fails identically:

- **`--github` with `--no-git` is refused.** `gh repo create --push` hard-errors on a repo with zero commits, so groot needs the initial commit that `--no-git` skips.
- **`--public` without `--github` is refused.** `--public` is only meaningful as a modifier of `--github`.
- **A git identity must exist.** Both `user.name` and `user.email` must be set globally (or via system config) — groot resolves the identity the same way the fresh `git init` will, so a caller repo's *local* identity doesn't count. When either half is missing, groot prints the exact fix:

  ```sh
  git config --global user.name "Your Name"
  git config --global user.email "you@example.com"
  ```

- **The target must not already be a git repository.** `--github` is for repositories groot itself creates and commits. When `.git` already exists, groot refuses up front and prints the manual `gh repo create …` command to run yourself once you've committed.

### The degrade-never-fail contract

Anything that goes wrong *after* generation degrades to printed next steps and **exits `0`** — the workspace on disk is already valid.

- **`gh` is missing from `PATH`.** groot prints the install link, `gh auth login`, and the full `gh repo create …` invocation as numbered next steps:

  ```text
  ●  GitHub CLI (gh) not found on PATH — the repository was not created.

  Next steps:
    1. cd my-app
    2. Install the GitHub CLI: https://cli.github.com
    3. gh auth login
    4. gh repo create my-app --private --source=. --remote=origin --push
    5. bun dev
  ```

- **`gh` is installed but not logged in.** `gh auth status` exits `1`, groot short-circuits before running `gh repo create`, and the next steps are `gh auth login` + the create command.
- **`gh repo create` fails** (for example, exit `4` when unauthenticated, or exit `1` when the name is taken). groot prints the first stderr line and the exit code, then the manual `gh repo create …` command.

In every failure case the run exits `0`, git history is intact, and you can copy-paste the printed command to finish publishing yourself.

## Next steps output

After a successful plant, groot prints a personalised next-steps block:

```text
Next steps:
  1. cd my-app
  2. bun run --cwd packages/backend setup   # Convex login + dev deployment (interactive)
  3. bun dev
```

The Convex login step is intentionally deferred — groot never runs interactive third-party auth flows itself; it only tells you when and how to run them.

## Exit codes

| Code | Meaning |
|---|---|
| `0` | Success |
| `1` | Unexpected internal error |
| `2` | Invalid flags or arguments |
| `3` | Preflight failure (Bun missing, directory conflict, offline) |
| `4` | Generator failure (upstream `create-*` command failed) |
| `5` | Stitch or verify failure |
| `130` | Cancelled at a prompt (Ctrl-C) |
