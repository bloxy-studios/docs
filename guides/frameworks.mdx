After groot finishes scaffolding, each framework lands in a ready-to-run state — but a few require a manual step or behave in ways worth knowing about. This page covers the post-scaffold notes and known gotchas for every framework groot supports, so you know exactly what to expect from `groot init` onward.

<Accordion title="Next.js">
  Next.js is groot's default web framework and the recommended pairing with Convex. groot generates it via `create-next-app@16` with the App Router, Tailwind v4, and Turbopack enabled.

  **What gets generated**

  - App Router layout under `apps/web/src/app/`
  - Tailwind v4 configured via `postcss.config.mjs`
  - Turbopack enabled by default for faster local development
  - `tsconfig.json` extended from `@repo/typescript-config/nextjs.json` — groot rewires this during the stitch stage

  **Running the dev server**

  Run `bun run dev` from the workspace root. Turborepo orchestrates all apps in parallel, so you do not need to `cd` into `apps/web` manually. The Next.js dev server starts on port **3000**.

  **AGENTS.md and CLAUDE.md**

  `create-next-app` generates `AGENTS.md` and `CLAUDE.md` in `apps/web` by default (the `--agents-md` flag is on unless you pass `--no-agents-md`). These are context files for AI coding agents. They are safe to delete if you do not use them — they have no effect on the build or runtime.

  <Note>
  If you are running groot in CI and want to suppress these files, they must be removed as a post-scaffold step. groot does not pass `--no-agents-md` so that the default experience matches what `create-next-app` produces out of the box.
  </Note>
</Accordion>

<Accordion title="SvelteKit">
  groot generates SvelteKit via the official `sv` CLI (the successor to the deprecated `create-svelte`). The scaffold uses the minimal template with TypeScript, Svelte 5, and Vite 8.

  **What gets generated**

  - `src/` with `app.html`, `app.d.ts`, `lib/`, and `routes/`
  - `vite.config.ts` — see the config note below
  - TypeScript config at `tsconfig.json`

  **SvelteKit config lives in vite.config.ts**

  There is no separate `svelte.config.js` file. As of `sv` 0.16, the SvelteKit configuration (adapters, compiler options) lives inside `vite.config.ts` as plugin options. If you are writing custom tooling or doctor checks that look for a SvelteKit config, look there — not at a standalone `svelte.config.js`.

  **The prepare script**

  The generated `package.json` includes a `prepare` script that runs `svelte-kit sync`. This fires automatically during root `bun install`. You will see it in install output — this is normal and expected.

  **Dev server**

  Run `bun run dev` from the workspace root. The SvelteKit app starts on port **5173** via Vite.

  **Adding SvelteKit add-ons**

  groot scaffolds SvelteKit without add-ons (`--no-add-ons`). To add official integrations after scaffolding, use:

  ```sh
  bunx sv add
  ```

  This gives you access to the full `sv` add-on catalog (auth, testing, Prettier, and so on) without re-scaffolding.
</Accordion>

<Accordion title="TanStack Start">
  groot generates TanStack Start via `@tanstack/cli@0.69` in `create` mode — the React framework with Vite under the hood.

  **What gets generated**

  - Vite-powered TanStack Start app under `apps/web/`
  - `vite.config.ts` with the `tanstackStart` plugin
  - A `dev` script pinned to port 3000 (`vite dev --port 3000`)

  **Suppressed generator options**

  groot passes `--no-toolchain` and `--no-intent` so the scaffold lands clean:

  - `--no-toolchain` skips the ESLint/Biome overlay the CLI would otherwise add. The workspace root owns linting, so per-app overlays would collide with root config.
  - `--no-intent` skips the TanStack CLI's own agent skill files (`.tanstack/`, `SKILL.md`). groot's agent artifacts arrive with roadmap v1.3 and must not collide with per-framework agent files.

  **Dev server**

  Port **3000**, shared with Next.js and Nuxt. If you grow a second web scaffold that also defaults to 3000, `groot add` emits a port collision warning and `groot doctor` flags it persistently.

  **Convex env plumbing**

  TanStack Start reads env vars through Vite's `import.meta.env`, so groot writes `VITE_CONVEX_URL` into `.env.example` when Convex is also selected.

  **Build output**

  `vite build` → `dist/`. The template has no Nitro or Vinxi dependencies — build is plain Vite.
</Accordion>

<Accordion title="Astro">
  groot generates Astro via `create-astro@5` using the `minimal` template. The template is fetched from the `withastro/astro` examples via giget at scaffold time.

  **What gets generated**

  - Minimal Astro app under `apps/web/`
  - `astro.config.mjs`
  - TypeScript-strict configuration

  **Suppressed generator options**

  - `--no-ai` skips Astro's AI agent config files. groot's agent artifacts arrive with roadmap v1.3, so per-framework agent files are suppressed across every web adapter (TanStack `--no-intent`, React Router `--no-agent-skills`, Astro `--no-ai`) — one unified policy.
  - `--skip-houston` disables the mascot animation so non-TTY output stays deterministic.

  **Dev server**

  Port **4321** — Astro's default and the only unique web port in the matrix. No port-sharing gotchas.

  **Convex env plumbing**

  Astro exposes public env vars with the `PUBLIC_*` prefix (`import.meta.env.PUBLIC_*`), so groot writes `PUBLIC_CONVEX_URL` into `.env.example`. SvelteKit uses the same prefix — if you ever mix an Astro and SvelteKit web scaffold, the `.env.example` entry is deduplicated per exact line.

  **Build output**

  `astro build` → `dist/`.

  <Warning>
    Under `--yes`, `create-astro` silently redirects a **non-empty** target directory to a randomly generated project name (via its internal `generateProjectName()`) instead of failing loudly. groot always scaffolds into a fresh destination, so the happy path always holds — but if you run `create-astro` yourself outside of groot, make sure the target is absent or empty.
  </Warning>
</Accordion>

<Accordion title="React Router">
  groot generates React Router (framework mode — the Remix successor) via `create-react-router@8`. The default template is fetched from `remix-run/react-router-templates` at scaffold time: TypeScript + Tailwind + SSR (with a Dockerfile, kept as-is).

  **What gets generated**

  - React Router framework-mode app under `apps/web/`
  - `react-router.config.ts` — the definitive framework-mode marker
  - `app/` directory with routes and layouts
  - Tailwind wired via Vite

  **Suppressed generator options**

  `create-react-router@8.2` added a step that copies React Router's own agent skill files (`SKILL.md` + references) into the project. groot passes `--no-agent-skills` to suppress it — the same policy applied to TanStack's `--no-intent` and Astro's `--no-ai`. groot's agent artifacts arrive with roadmap v1.3 and must not collide with per-framework agent files.

  **Dev server**

  Port **5173** — the Vite default, shared with SvelteKit and Vite. Multiple `5173`-defaulting web scaffolds in one workspace trigger a `groot add` collision warning and are flagged by `groot doctor` until you change one app's `package.json` dev script.

  **Convex env plumbing**

  `VITE_CONVEX_URL` — React Router 7+ runs on Vite and consumes env vars through `import.meta.env`.

  **Build output**

  `react-router build` → `build/` (client bundle + server bundle).
</Accordion>

<Accordion title="Nuxt">
  groot generates Nuxt via `create-nuxt@3` using the `minimal` template. The template is fetched from `nuxt/starter` via giget at scaffold time. Note that the CLI package is 3.x even though Nuxt itself is v4.

  **What gets generated**

  - Nuxt app under `apps/web/`
  - `nuxt.config.ts`
  - `app/` directory (Nuxt 4 layout)

  **The four mandatory non-interactive arguments**

  <Warning>
    `create-nuxt` has no `--yes` flag. In non-interactive mode, the CLI **requires** an explicit choice for all four of: the positional directory, `--template`, `--packageManager`, and a git-init decision. Omit any of the four and the CLI exits with code `2`. groot always passes all four:

    ```text
    bunx create-nuxt@3 <name> \
      --template minimal --packageManager bun --no-gitInit \
      --no-install --no-modules
    ```

    `--no-gitInit` is citty's auto-negation of `--gitInit` — it counts as an explicit decision. `--no-modules` skips the module-selection prompt. If you invoke `create-nuxt` yourself in a script, mirror this shape or the CLI will exit non-interactively before scaffolding anything.
  </Warning>

  **The prepare script**

  The generated `package.json` includes `"postinstall": "nuxt prepare"`. This runs during the root `bun install` as a workspace-local script — you will see it in install output. This is expected and harmless.

  **Dev server**

  Port **3000** — shared with Next.js and TanStack Start. Multiple `3000`-defaulting scaffolds trigger a port collision warning and are flagged by `groot doctor`.

  **Convex env plumbing**

  `NUXT_PUBLIC_CONVEX_URL` — matches Nuxt's `useRuntimeConfig().public.*` client prefix.

  **Build output**

  `nuxt build` → `.output/` (Nitro's server bundle). This path is added to Turborepo's outputs so builds are cached correctly.
</Accordion>

<Accordion title="Vite">
  groot generates a plain Vite React SPA via `create-vite@9` using the `react-ts` template. This is the "no meta-framework" web option — for when a router and SSR are more than the job needs.

  **What gets generated**

  - React + TypeScript SPA under `apps/web/`
  - `vite.config.ts`
  - Oxlint configuration (see below)

  **Suppressed generator options**

  - `--no-interactive` forces non-interactive mode.
  - `--no-immediate` opts out of `create-vite@9`'s immediate mode, which would install dependencies **and** start the dev server. groot never runs generators that block waiting for input.

  **Oxlint by default**

  As of `create-vite@9`, React templates ship with [Oxlint](https://oxc.rs/docs/guide/usage/linter) configured. groot keeps this as-is because the workspace root owns linting anyway — the per-app Oxlint config is harmless and coexists with root ESLint/Biome if you use them.

  **`_gitignore` rename**

  `create-vite` ships its gitignore as `_gitignore` and renames it to `.gitignore` on copy. This is normal Vite generator behaviour, not a groot patch.

  **Dev server**

  Port **5173** — the Vite default, shared with SvelteKit and React Router. Same port-sharing behaviour: `groot add` warns on collision and `groot doctor` flags it persistently.

  **Convex env plumbing**

  `VITE_CONVEX_URL`.

  **Build output**

  `vite build` → `dist/`.
</Accordion>

<Accordion title="Expo">
  groot generates an Expo project via `create-expo-app@4` using the `default@sdk-57` template, which includes Expo Router and TypeScript.

  **What gets generated**

  - Expo Router setup under `apps/mobile/`
  - TypeScript configuration
  - Metro dev server configuration

  **Metro and bun workspaces**

  Since Expo SDK 52, Metro **auto-configures** itself for bun workspaces. You do not need to add legacy `metro.config.js` hacks such as `watchFolders` or `nodeModulesPath` — those are outdated patterns. If you see them in older guides, skip them.

  Shared workspace packages are consumed using the workspace protocol:

  ```json
  {
    "@repo/ui": "*"
  }
  ```

  **Dev server**

  The Metro dev server runs on port **8081**. Start it with `bun run dev` from the workspace root or `cd apps/mobile && bun run start`.

  **No git-suppression flag**

  `create-expo-app` does not have a flag to suppress `git init`. groot runs the Expo generator after the workspace root already exists as a git repo (so Expo's generator behaves like `create-next-app` inside an existing repo) and then verifies that no nested `.git` directory was created. This is checked persistently by `groot doctor`.

  <Warning>
  During the SDK 57 transition period, omitting `--template` from `create-expo-app` yields an SDK 54 project. groot always pins the template tag explicitly (`default@sdk-57`) to avoid this. If you are running the generator manually outside of groot, make sure to pin the template tag.
  </Warning>
</Accordion>

<Accordion title="Elysia">
  groot does not use a third-party generator for Elysia. The community `create-elysia` package is not used because it is not an official Elysia org package, uses interactive prompts with no bypass flags, and diverges from Elysia's own documentation. Instead, groot writes the four files from Elysia's official manual setup directly.

  **What gets written**

  ```
  apps/api/
  ├── src/index.ts       # new Elysia().get("/", …).listen(3001)
  ├── package.json       # dev / build / start / test scripts
  ├── tsconfig.json      # strict: true
  └── README.md
  ```

  **Scripts**

  | Script | Command |
  |--------|---------|
  | `dev` | `bun --watch src/index.ts` |
  | `build` | `bun build src/index.ts --target bun --outdir ./dist` |
  | `start` | `NODE_ENV=production bun dist/index.js` |
  | `test` | `bun test` |

  **Dev server**

  The Elysia server listens on port **3001**.

  **Extending with plugins**

  Elysia has a rich plugin ecosystem for things like JWT auth, Swagger, rate limiting, and more. Browse available plugins at [elysiajs.com](https://elysiajs.com).
</Accordion>

<Accordion title="Hono">
  groot generates Hono via `create-hono@0.19` using the `bun` template. This gives you a minimal Hono server configured for the Bun runtime.

  **What gets generated**

  - `src/index.ts` with `export default app`
  - `package.json` with `dev: bun run --hot src/index.ts` and `hono ^4.12`
  - `tsconfig.json`

  **Dev server**

  The Hono server listens on port **3001**.

  **Port collision with Elysia**

  Both Hono and Elysia default to port 3001. If your workspace contains both (for example, Elysia at `apps/api` and Hono at a custom `--path`), groot emits a warning during `groot add` and `groot doctor` will flag the collision persistently until you change one of the ports.

  Run `groot doctor` to see the warning and the suggested fix:

  ```sh
  groot doctor
  ```

  <Note>
  Hono is runtime-agnostic by design. Even though groot scaffolds it with the Bun template, you can deploy the same code to Cloudflare Workers, Node.js, Deno, and other runtimes later without rewriting your route handlers.
  </Note>
</Accordion>

<Accordion title="Convex">
  groot writes the Convex backend package directly — there is no upstream generator used. This is because no fully offline official Convex generator exists, and groot needs to vendor `_generated` stubs so the package typechecks before any login or deployment provisioning.

  **What gets written**

  ```
  packages/backend/
  ├── convex/
  │   ├── schema.ts           # starter schema (messages table)
  │   ├── messages.ts         # starter query + mutation
  │   ├── tsconfig.json       # vendored from get-convex/templates
  │   └── _generated/         # vendored standard stubs — committed
  ├── package.json            # @repo/backend · dev / setup / typecheck scripts
  └── .env.example            # CONVEX_DEPLOYMENT / CONVEX_URL placeholders
  ```

  The package name is `@repo/backend`. This is fixed by workspace conventions — you cannot use `--path` with `groot add convex` to place a second Convex package at a custom path (the backend slot is single-occupancy).

  **First-time login — groot does NOT run this**

  groot intentionally does not run `bunx convex dev`. The first-time login, deployment provisioning, and `.env.local` generation are interactive steps that cannot be automated without credentials. Instead, groot prints this as the first item in the "next steps" block after scaffolding:

  ```sh
  # Run this once to authenticate and provision your Convex deployment
  bunx convex dev --until-success
  ```

  The `--until-success` flag runs Convex just long enough to complete login and deployment provisioning, then exits — it does not start a persistent watch process. You only need to do this once per project. After that, `bun run dev` from the workspace root handles everything.

  **Vendored _generated stubs**

  The `convex/_generated/` directory is committed to source control — this is the official Convex recommendation, and it is what allows the package to typecheck before any deployment exists. The first real `convex dev` run regenerates these stubs against your live deployment.

  Run `groot doctor` to verify that the `_generated` stubs are in sync with your schema:

  ```sh
  groot doctor
  ```

  <Warning>
  The backend slot is single-occupancy. The package name `@repo/backend` is fixed by workspace conventions, so `--path` cannot be used to escape the occupancy constraint when running `groot add convex`. If your workspace already has a Convex backend, `groot add convex` exits 2 with an explanation.
  </Warning>
</Accordion>
