When you run `bun create groot`, groot doesn't copy files from a set of frozen templates. Instead, it orchestrates each framework's *own* official generator, intercepts the output, and surgically patches everything into a single coherent bun workspace. The result is a monorepo that always reflects today's upstream frameworks — not a snapshot from the last time someone updated a template.

The full pipeline has five internal stages, but from the outside you can think of it as three meaningful phases: **Generate**, **Stitch**, and **Verify**.

<Note>
  groot uses `create-turbo` to plant the Turborepo workspace skeleton first — complete with `packages/typescript-config`, `turbo.json`, and a bun-flavored root `package.json`. It then immediately removes the example `apps/web`, `apps/docs`, `packages/ui`, and `packages/eslint-config` that `create-turbo` adds, and replaces them with the scaffold selections you chose. The shared `packages/typescript-config` is kept and extended by every app groot grows.
</Note>

## The three-phase pipeline

<Steps>
  <Step title="Generate — run official generators, not groot templates">
    groot runs each selected framework's official generator with a pinned major version and a full set of non-interactive, silence flags: no git init, no install, no writes outside the target directory. You get the exact scaffold those generators produce today.

    | Framework | Generator invoked |
    |-----------|-------------------|
    | Next.js   | `create-next-app@16` |
    | SvelteKit | `sv@0.16` |
    | Expo      | `create-expo-app@4` |
    | Tauri     | `create-tauri-app@4` |
    | Electron  | `@quick-start/create-electron@1` |
    | Hono      | `create-hono@0.19` |

    **Two deliberate exceptions** where groot writes files directly instead of shelling out to a generator:

    - **Elysia** — `bun create elysia` resolves to a community-owned package whose template diverges from Elysia's own documented setup (the `dev` script is missing). groot writes the four files straight from Elysia's official manual-setup docs: `src/index.ts`, `package.json`, `tsconfig.json`, and `README.md`.
    - **Convex** — no fully-offline official generator exists, and `convex codegen` requires a configured deployment in current releases. groot writes `packages/backend` directly, including the standard `convex/_generated` stubs vendored from Convex's own reference templates, so the package typechecks before any login.

    Because groot pins generator *majors* (not exact versions), you always get the latest patch within that series. Bumping to a new major is an explicit, reviewed, changelogged groot release — so the goalposts never move on you silently.
  </Step>

  <Step title="Stitch — patch N independent scaffolds into one workspace">
    Raw generator output is a collection of standalone apps that have never heard of each other. The stitch stage applies a deterministic set of pure transforms that turn them into a real bun Turborepo workspace.

    | Operation | What groot does |
    |-----------|-----------------|
    | **Workspace globs** | Adds `"workspaces": ["apps/*", "packages/*"]` and `"packageManager": "bun@<pinned>"` to the root `package.json` |
    | **Package naming** | Apps get bare names (`web`, `mobile`, `api`); shared packages get the `@repo/*` namespace (`@repo/backend`, `@repo/typescript-config`) |
    | **TypeScript config** | Next.js is rewired to extend `@repo/typescript-config/nextjs.json`; the shared `packages/typescript-config` package is kept from the Turborepo trunk for all apps to build on |
    | **Port allocation** | Deterministic, non-colliding dev ports are written into each app — web at `3000`, mobile at `8081`, desktop (Tauri) at `1420`, API at `3001`. Electron declares no port (self-wiring). |
    | **Lockfile hygiene** | Any per-app lockfiles left behind by generators are deleted; exactly one root `bun.lock` remains |
    | **`.gitignore`** | Per-app `.gitignore` files stay in place (native git semantics); the root `.gitignore` is topped up to cover workspace basics |
    | **`turbo.json`** | Root tasks (`dev`, `build`, `lint`, `check-types`) are written with correct `outputs` per framework |
    | **Env plumbing** | `.env.example` entries are added per scaffold (e.g. `NEXT_PUBLIC_CONVEX_URL`, `EXPO_PUBLIC_CONVEX_URL` when Convex is selected) |
    | **`groot.json`** | A manifest is written at the workspace root recording every scaffold, its generator pin, path, and dev port |

    Every stitch transform is a pure function of the generated file tree and the resolved plan — no network calls, no ambient state — so they're fully unit-testable without running generators.
  </Step>

  <Step title="Verify — confirm the workspace coheres, then install">
    After stitching, groot runs a round of structural checks: every `package.json` must parse correctly, package names must be unique across the workspace, and workspace globs must match the actual directory layout.

    Assuming the checks pass, groot runs `bun install` at the workspace root (skip with `--no-install`), then creates an initial git commit (skip with `--no-git`). Finally, a summary report is printed — including any deferred steps like the `bunx convex dev --until-success` login when Convex was selected.

    You can re-run the health checks any time after scaffolding with:

    ```bash
    groot doctor
    ```

    `groot doctor` re-reads `groot.json` and runs every per-framework check registered by its adapter, including Convex `_generated` sync, port collision detection, and turbo task resolution.
  </Step>
</Steps>

## Why orchestrate instead of template?

Scaffolding CLIs face a fork: ship your own templates and own the maintenance burden of every upstream change, or run official generators and deal with moving targets. groot chooses the second path and mitigates the risk three ways:

1. **Pinned generator majors** — flags can only break within a major. groot bumps majors deliberately.
2. **Thin flag adapters** — each generator's invocation lives in one small module. When upstream changes a flag, only that module needs updating.
3. **A written contract per generator** — for each generator, every verified flag, output shape, and monorepo caveat is recorded alongside a verification date. Drift is caught by re-verifying those facts, not by archaeology.

The alternative — vendored templates — means every upstream release is your maintenance burden. groot bets that orchestrating upstream generators and tracking their flags is a smaller surface to maintain than forking their output.
