---

groot organises its framework choices into four **slots** — `web`, `mobile`, `api`, and `backend`. Each slot maps to a fixed workspace location, a deterministic dev port, and an upstream generator (or a set of files groot writes directly). You pick at most one framework per slot when you run `groot init`, and you can grow additional scaffolds into custom paths later with `groot add`.

## Matrix

| Slot | Framework | Location | Dev Port | Generator |
|------|-----------|----------|----------|-----------|
| `web` | Next.js | `apps/web` | 3000 | `create-next-app@16` |
| `web` | SvelteKit | `apps/web` | 5173 | `sv@0.16` |
| `mobile` | Expo | `apps/mobile` | 8081 | `create-expo-app@4` |
| `api` | Elysia | `apps/api` | 3001 | *(files written directly)* |
| `api` | Hono | `apps/api` | 3001 | `create-hono@0.19` |
| `api` | Fastify | `apps/api` | 3001 | `fastify-cli@8` |
| `backend` | Convex | `packages/backend` | — | *(files written directly)* |
| `backend` | Supabase | `packages/backend` | — | `supabase@2 init` (postCommand) |

<Note>
  Each slot can hold only one framework at a time by default. To grow a second web app — for example, a marketing site alongside your main product — use `groot add --path apps/marketing` to scaffold it into a custom path that doesn't conflict with an occupied slot.
</Note>

## Framework details

### Next.js

groot invokes `create-next-app@16` with App Router, Tailwind v4, TypeScript, Turbopack, and `--use-bun` so the generated lockfile and scripts are bun-native from the start. ESLint is included. After generation, groot patches `tsconfig.json` to extend `@repo/typescript-config/nextjs.json` — the shared TypeScript config from the Turborepo trunk — so type-checking is consistent across the workspace.

Dev port `3000` is Next.js's default and is kept as-is. The `NEXT_PUBLIC_CONVEX_URL` env var is plumbed into `.env.example` when Convex is also selected.

```bash
# What groot runs
bunx create-next-app@16 apps/web \
  --ts --tailwind --eslint --app --src-dir --turbopack \
  --import-alias "@/*" --use-bun --skip-install --disable-git --yes
```

### SvelteKit

groot invokes the official `sv` CLI (the successor to the deprecated `create-svelte`) with the minimal template, TypeScript, and no add-ons. The generated project uses Svelte 5, SvelteKit 2, and Vite 8. groot then adds `check` and `check-types` scripts to align with Turborepo conventions, and folds the per-app `.gitignore` and `.npmrc` into the workspace root.

<Tip>
  SvelteKit's generated `prepare` script (`svelte-kit sync || echo ''`) runs during root `bun install`. This is expected and harmless — you'll see it in install output.
</Tip>

Vite's default port `5173` is kept. Note that SvelteKit config now lives inside `vite.config.ts` as plugin options — there is no separate `svelte.config.js` in the generated output.

```bash
# What groot runs
bunx sv@0.16 create apps/web \
  --template minimal --types ts --no-add-ons --no-install --no-dir-check
```

### Expo

groot invokes `create-expo-app@4` with the `default@sdk-57` template, which gives you Expo Router, SDK 57, and TypeScript. The template tag is pinned explicitly — omitting it during the SDK 57 transition produces an SDK 54 project.

Expo has first-class bun-workspace support since SDK 52, and Metro **auto-configures** for monorepos in current releases. groot does not write legacy `metro.config.js` workspace hacks (`watchFolders`, `nodeModulesPath`, etc.) — those are no longer needed. Shared packages are consumed as `"<pkg>": "*"` in the Expo app's `package.json`.

The Metro dev server runs on port `8081` (Metro's default, kept as-is).

```bash
# What groot runs
bunx create-expo-app@4 apps/mobile \
  --template default@sdk-57 --no-install --yes
```

### Elysia

No reliable upstream generator exists for Elysia: `bun create elysia` resolves to a community-owned package that diverges from Elysia's own documented setup (the `dev` script is absent). Instead, groot writes four files directly, taken straight from Elysia's official manual-setup documentation.

```text
apps/api/
├── src/index.ts       # new Elysia().get("/", …).listen(3001)
├── package.json       # dev · build · start · test scripts
├── tsconfig.json      # strict: true
└── README.md
```

The server is set to listen on port `3001` (patched from Elysia's default of `3000`). Scripts follow Elysia's documented layout:

| Script | Command |
|--------|---------|
| `dev` | `bun --watch src/index.ts` |
| `build` | `bun build src/index.ts --target bun --outdir ./dist` |
| `start` | `NODE_ENV=production bun dist/index.js` |
| `test` | `bun test` |

Dependencies: `elysia@^1.4` and `@types/bun`.

### Hono

groot invokes `create-hono@0.19` with the `bun` template and `--pm bun`. The template is fetched from the `honojs/starter` repository, pinned to a tag that matches `create-hono`'s own major.minor — deterministic per CLI version.

After generation, groot rewrites the default export in `src/index.ts` to `export default { port: 3001, fetch: app.fetch }`, changing the default port from `3000` to `3001`. `build` and `start` scripts are added to mirror the Elysia layout.

```bash
# What groot runs
bunx create-hono@0.19 apps/api --template bun --pm bun
```

### Fastify

groot invokes `fastify-cli@8 generate` with `--lang=ts --esm` to pin the ESM TypeScript template. The generator ships a single bin named `fastify` (not the same as the package name) — bunx's single-bin fallback handles it. The template is fully non-interactive: no prompts, no install, no git init.

<Warning>
  `fastify-cli generate` unconditionally shells out to `npm init -y` inside the target directory to derive the package name. That call fails with `EBADDEVENGINES` when it walks up into the bun-declared workspace root that Turborepo writes. groot works around this by running the generator in a disposable staging directory under the OS tempdir, then moving the output into `apps/api`.
</Warning>

The `--lang=ts --esm` template lands an `@fastify/autoload` app plugin at `src/app.ts` alongside `src/plugins/` and `src/routes/`, plus a node:test suite. `@fastify/autoload` ≥ 6 detects Bun natively and loads `.ts` routes with no compile step, so nothing in the runtime chain requires ts-node.

The template normally serves the app through the Node-centric `fastify start` wrapper. groot instead overlays `src/server.ts` — modelled on fastify-cli's own eject template — which registers the app plugin and listens on port `3001`. Scripts are then swapped for the bun set:

| Script | Command |
|--------|---------|
| `dev` | `bun --watch src/server.ts` |
| `build` | `tsc` (emits to `dist/`, turbo-cached) |
| `start` | `bun dist/server.js` |
| `test` | `bun test` |
| `typecheck` | `tsc --noEmit` |

The script rewrite is marker-gated on the template's own `dev` script, so re-runs are idempotent and hand-rolled scripts are never clobbered. Template devDependencies are left untouched.

```bash
# What groot runs (in a staged tempdir, then moved into apps/api)
bunx fastify-cli@8 generate api --lang=ts --esm
```

### Convex

No fully-offline official generator exists for Convex — `convex codegen` requires a configured deployment in current releases. groot writes `packages/backend` directly, modelling the output on Convex's own reference monorepo.

```text
packages/backend/
├── convex/
│   ├── schema.ts          # starter schema (messages table)
│   ├── messages.ts        # starter query + mutation
│   ├── tsconfig.json
│   └── _generated/        # vendored standard stubs — committed to git
├── package.json           # @repo/backend · dev · setup · typecheck
└── .env.example           # CONVEX_DEPLOYMENT / CONVEX_URL placeholders
```

The `convex/_generated` stubs are vendored and committed — the same strategy Convex's own templates use — so the package typechecks before any login. The first `bunx convex dev --until-success` run regenerates them against your live deployment.

<Note>
  groot never runs `convex dev` for you. Because deployment provisioning and Convex login are unavoidably interactive, groot prints `bunx convex dev --until-success` as your first "next step" after scaffolding and leaves it to you to run when you're ready.
</Note>

Apps that consume the backend depend on `"@repo/backend": "workspace:*"` and deep-import `@repo/backend/convex/_generated/api` directly — there is no `exports` map on the backend package, which matches the pattern Convex's reference monorepo uses.

### Supabase

Supabase runs locally through Docker, so there is no cloud port to allocate at scaffold time — the local stack takes Supabase's own `54321+` block whenever you start it, which is why the matrix leaves the port column blank. groot uses a two-part layout: it writes the `@repo/backend` package shell first, then runs `bunx supabase@2 init` as a `postCommand` inside that package so the official CLI drops `supabase/config.toml` next to groot's own files.

**What groot writes (before `supabase init` runs)**

```text
packages/backend/
├── package.json              # @repo/backend · dev · stop · typegen · typecheck scripts
├── database.types.ts         # placeholder matching `supabase gen types` output for an empty schema
├── .env.example              # SUPABASE_URL / SUPABASE_ANON_KEY placeholders (values left empty)
├── tsconfig.json
└── README.md                 # Docker / login / typegen next-steps
```

The `database.types.ts` placeholder follows the Convex vendored-stubs pattern — apps that deep-import `@repo/backend/database.types` typecheck immediately, before Docker is ever started. When you eventually run `bun run typegen`, the Supabase CLI regenerates the file against your live schema.

Scripts on the `@repo/backend` package:

| Script | Command |
|--------|---------|
| `dev` | `supabase start` (boots the local Docker stack) |
| `stop` | `supabase stop` |
| `typegen` | `supabase gen types typescript --local > database.types.ts` |
| `typecheck` | `tsc --noEmit` |

**What `supabase init` writes**

`bunx supabase@2 init` runs as a post-command with its working directory pinned to `packages/backend`. It has no directory argument — it always writes `supabase/` into its cwd — which is why groot creates the package shell first. The 2.x CLI is non-interactive by default (the old IDE prompts moved behind an opt-in `--interactive` flag that also requires a TTY), so the run is safe in CI.

<Note>
  Docker is not started, `supabase login` is not run, and real codegen is not attempted during scaffolding. All three are deferred to the "next steps" block after generate — mirroring the Convex login pattern. `.env.example` values stay empty because `supabase start` prints the real keys on first boot; no secrets are ever vendored.
</Note>

**Stitching**

groot's stitch stage rewrites `supabase/config.toml`'s `project_id` field — which defaults to the cwd basename (`"backend"`) — to your workspace name. The `project_id` names Docker containers, so leaving it at `"backend"` would collide any time you ran two groot workspaces on the same host.

Env plumbing is per-frontend, using the same public-env prefixes as Convex. For each frontend in the workspace, groot writes two lines to that app's `.env.example`:

| Framework | Env vars written |
|-----------|------------------|
| Next.js | `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` |
| SvelteKit, Astro | `PUBLIC_SUPABASE_URL`, `PUBLIC_SUPABASE_ANON_KEY` |
| TanStack Start, React Router, Vite | `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` |
| Nuxt | `NUXT_PUBLIC_SUPABASE_URL`, `NUXT_PUBLIC_SUPABASE_ANON_KEY` |
| Expo | `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY` |
| React Native (bare) | `SUPABASE_URL`, `SUPABASE_ANON_KEY` |

**Doctor checks**

`groot doctor` runs two Supabase-specific checks:

- `supabase/config.toml` exists inside `packages/backend`.
- `database.types.ts` exists — if it is still the empty-schema placeholder, doctor emits a warning pointing at `bun run --cwd packages/backend typegen` so the file tracks your live schema.

**Next steps output**

After scaffolding, `printNextSteps` includes the Docker line — `groot add supabase` prints the same hint so the CLI's guidance stays symmetric with `groot init`:

```sh
bun run --cwd packages/backend dev   # supabase start (Docker required)
```

Apps that consume the backend depend on `"@repo/backend": "workspace:*"` and deep-import `@repo/backend/database.types` directly, matching the deep-import pattern Convex uses.
